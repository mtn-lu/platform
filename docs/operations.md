# Operations — deployment is opt-in

## Local development

Use the README startup sequence. `.dev.vars` contains newly generated local-only secrets. Wrangler persists local D1 under `.wrangler/state`; the local-only dev_email table is created with `npm run email -- setup`. `npm run email -- read` prints the most recent synthetic/local login email to your terminal. Treat even development links as credentials. No public inbox route or production logging fallback exists. Keep your dev server on loopback; the Vite tooling exposes local development inspection capabilities that must never be publicly hosted.

Grant and revoke with `npm run access -- grant ADDRESS` / `revoke ADDRESS`. Inputs are trimmed/lowercased, without provider-specific dot/plus normalization. The CLI writes a permission-restricted temporary SQL file with tested literal escaping, launches Wrangler without a shell, and deletes the file. Remote access changes require `--remote` plus a successful production preflight; none were run for this scaffold.

The bounded hourly scheduled handler deletes up to 500 expired verification, session and throttle records each, and local capture rows where applicable. For a local manual tick, use Wrangler's scheduled-event test support (`wrangler dev --test-scheduled` and its local `/__scheduled` endpoint). This endpoint belongs to local tooling, not the deployed application. For production backlog recovery, temporarily increase invocation frequency through a reviewed config change or run reviewed bounded SQL deletes through Wrangler. Monitor D1 row growth and delivery failure counts if the audience expands.

## Prepare production (owner actions, not performed)

1. Control the mtn.lu DNS zone in Cloudflare. Inventory every subdomain and ensure all backends/content are trusted. Do not create an mtn.lu cookie for previews. Use a completely separate domain, database and secrets for any future preview deployment.
2. Create one D1 identity database in the intended Cloudflare account using the dashboard or `wrangler d1 create mtn-platform-identity`. Record its actual ID. No app databases belong in this repository.
3. Copy `docs/wrangler.production.example.jsonc` to ignored `wrangler.production.jsonc` in the repository root. Replace all placeholders, including account/database IDs and verified sender. Set only the exact approved return origins; games is not approved until that app exists. Keep workers_dev=false and preview_urls=false. Use only the intended root custom-domain route. Remove/disable any old unintended routes or deployments in the account dashboard; repository config cannot revoke existing surfaces elsewhere.
4. Onboard your sender domain to Cloudflare Email Service beta and complete its documented domain/account checks. Do not invent a verified sender. Configure the EMAIL binding; the adapter uses `EMAIL.send({to,from,subject,text,html})`, one recipient, no tracking pixels or rewritten tracking links. Its API has no tracking toggle in the verified structured builder. Confirm any account-level tracking or rewriting settings remain disabled for auth mail. No retries or provider response bodies are exposed to users.
5. Generate **independent** high-entropy AUTH_SECRET and THROTTLE_SECRET using a password manager or secure local generator, and supply them with `wrangler secret put NAME --config wrangler.production.jsonc`. Never paste secrets into chat or commit them. Preview/test secrets must differ. Run `npm run preflight` with the required secrets injected privately into the local process environment. It rejects incomplete IDs, unsafe origins, missing secrets, capture mode and unintended public routes. It checks local configuration only, not whether remote secrets/bindings actually exist: verify names/bindings in the account before deployment.
6. Back up existing D1 before risky migrations. Apply reviewed SQL explicitly with `wrangler d1 migrations apply DB --remote --config wrangler.production.jsonc`. `npm run db:migrate` is local; neither HTTP requests nor startup migrate production.
7. After an explicit deployment decision, build from a clean checkout with `PLATFORM_CONFIG=wrangler.production.jsonc npm run build`, then deploy the **generated** Worker config in `dist/<normalized-worker-name>/wrangler.json` using Wrangler. Do not deploy the local config or the types-only placeholder production environment in wrangler.jsonc. Do not copy development `.dev.vars` into this clean deployment checkout. Inspect the generated config/assets before uploading. This scaffold supplies no automatic deployment workflow.
8. Grant membership with the explicit remote operator command, then perform a real deliverability/login/logout/revocation smoke test using an owner-controlled account. Synthetic local tests do not prove DNS/email delivery or production CPU use. Review limits, actual CPU, D1 reads/writes, storage and email charges after launch.

### Email plans (verified 2026-09-06)

Cloudflare documents Email Sending as beta. Sending to account-verified destination addresses is free on all plans; sending to arbitrary recipients requires Workers Paid. Published paid email allocation is 3,000/month, then $0.35/1,000. Workers and D1 have separate usage limits/billing; free allocations can change. Local development/tests require no paid plan. See [Email API](https://developers.cloudflare.com/email-service/api/send-emails/workers-api/), [pricing](https://developers.cloudflare.com/email-service/platform/pricing/) and [domain configuration](https://developers.cloudflare.com/email-service/configuration/domain-configuration/). Recheck beta availability and current requirements in your account before choosing a plan. A later Resend adapter can implement the small transport interface; none is installed.

## Backup, recovery and rollback

Export before a risky migration: `wrangler d1 export DB --remote --config wrangler.production.jsonc --output /SAFE/PRIVATE/PATH/identity.sql`. Keep exports encrypted/access-controlled outside this public repo: they contain identities, reusable session tokens and verification records. Local export uses `--local`. Never copy a real export into fixtures.

To rehearse restore, create an isolated recovery D1 database, point a separate nonproduction config at it, then use `wrangler d1 execute DB --remote --config RECOVERY_CONFIG --file PRIVATE_EXPORT.sql` after reviewing the export and destination. Verify schema/row counts and access behavior before switching a production binding. Import into an empty recovery database, not blindly over a live database. Review Cloudflare D1 Time Travel availability and its retention in your account as an additional recovery path; do not assume unlimited retention.

Code rollback: redeploy the previous reviewed Worker build/config or use Wrangler's version rollback. A code rollback does **not** reverse SQL migrations. Prefer backward-compatible additive migrations; destructive rollback requires a separately reviewed recovery plan and may lose writes since backup. Export/migrate/restore commands remain explicit operator actions.

For session compromise, revoke the affected user's sessions or revoke membership immediately. For broad compromise, invalidate sessions and outstanding verification records through reviewed SQL, rotate AUTH_SECRET, and investigate every trusted subdomain. Rotating AUTH_SECRET invalidates signed browser cookies, but retaining exposed session rows is unnecessary risk. Rotate THROTTLE_SECRET separately; this resets effective rate-limit keys until old rows expire. Restoration may resurrect old credentials, so clear sessions/verification before reopening a recovered database when appropriate.
